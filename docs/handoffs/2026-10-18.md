## Tier 2 — built, validated, wired in

`conversion-tool/tier2_engine.py` translates PromQL patterns Tier 1 can't
parse (regex filters, label exclusions, `sum without(...)`) into a single
unified ES|QL query using `EVAL` + `CASE`, via a local Ollama model
(`qwen2.5-coder:7b`).

Validated live, in stages, against a real Elastic Cloud Serverless project:
1. The `IN (...)` grouping mechanism, using real macOS CPU modes as a
   stand-in for `irq`/`softirq` (which don't exist on macOS).
2. The actual AI-generated query for the real panel, end to end.
3. Cross-checked against Grafana's native PromQL rendering of the same
   underlying data — consistently within a couple of percentage points.

Three real model failures were found and fixed (see training guide §4 for
full detail): SQL-style `CASE WHEN` instead of ES|QL's `CASE(...)` function,
chained `STATS` commands (structurally broken — each `STATS` consumes the
prior stage's columns), and single-quoted strings (ES|QL requires double
quotes; likely confusion with Elasticsearch SQL, which uses single quotes).
All three are now covered by regression tests in `--selftest` using the
actual broken output that was produced.

Output columns are standardized (`metric_value`, `category`) regardless of
panel domain, so downstream code doesn't need to parse arbitrary AI-chosen
names. `$job` resolves via an explicit fallback (`DEFAULT_JOB_RESOLUTION` /
`PROM_JOB_NAME` env var) rather than silently dropping the filter the way
Tier 1 does.

`translate_tier2()` now retains a full `attempt_history` (every attempt, not
just the final one) — this was a late addition, built specifically to
support the Streamlit UI's auditability feature (see below).

## convert_panel.py — Tier 2 wired in as one coherent tool

`build_esql_timeseries_query()` now auto-escalates to Tier 2 when it finds
unsupported targets, instead of silently dropping them. `--tier1-only` CLI
flag preserves the old partial-conversion behavior for debugging/comparison.
`convert_panel()` now returns a 3-tuple `(kibana_panel, esql_query,
tier2_info)` — `tier2_info` is `None` for Tier 1 conversions, otherwise the
full result dict including `attempt_history`.

## Reference demo — both tools, kept in sync

- `build_demo_dashboard.py` builds all 3 panels (CPU Busy, CPU Cores, CPU
  Basic) into one Kibana dashboard. Uses a **fixed dashboard ID**
  (`prom-demo-reference-dashboard`) + `overwrite=true`, so re-running always
  updates the same object instead of creating duplicates.
  - This replaced an earlier find-by-title-then-delete approach, which
    turned out to depend on the Saved Objects `_find` API — unavailable on
    Elastic Cloud Serverless (`400: exists but is not available with the
    current configuration`), and more broadly a deprecated API surface
    across the Elastic Stack. Overwrite-by-id is the correct pattern, not a
    workaround.
- `grafana/provisioning/dashboard-files/cpu-busy.json` has the matching
  Grafana-side reference dashboard (all 3 panels, including the 6-target
  CPU Basic).
- Side-by-side comparison confirmed matching values across both: CPU Busy
  ~65% in both, CPU Cores 14 in both, CPU Basic band percentages within a
  few points.

## Streamlit UI — Stage 1 complete

`conversion-tool/app.py`. Upload/paste a panel, convert via the same
`convert_panel()` the CLI uses, see the ES|QL and a tier badge, import to
Kibana.

The non-trivial feature: **Tier 2 auditability**, built in from the start
rather than retrofitted. Whenever Tier 2 fires, an expandable "What the AI
did" section shows the explanation, approximations, and the full attempt
history — every attempt with its own pass/fail status and viewable ES|QL.
Reasoning: Tier 1 is a deterministic function you can trust by inspection;
Tier 2 isn't, and "succeeded after 2 retries" is a meaningfully different
signal from "succeeded on attempt 1" for anyone deciding whether to trust an
AI-generated query in a real migration.

Tested via Streamlit's headless `AppTest` utility (both the Tier 1 path and
a mocked multi-attempt Tier 2 path), then validated live in a real browser.

## Environment gotchas hit and fixed this session

(Full detail in training guide §6 — summarized here for quick reference.)

- A stale Docker container (`prom-demo-node-exporter`, never successfully
  started, left over from a prior Docker Desktop VM state) failed with a
  cryptic mount error. Fix: `docker rm` it, don't debug it.
- Node Exporter moved from a `/tmp` binary (doesn't survive reboots) to
  Homebrew (`brew install node_exporter && brew services start
  node_exporter`) — more durable going forward.
- Grafana's `GF_SECURITY_ADMIN_PASSWORD` only applies on first volume
  creation; admin/admin stopped working after the volume persisted across
  restarts. Fixed via `docker exec -it prom-demo-grafana grafana cli
  admin reset-admin-password admin` (note: `grafana cli`, not the older
  `grafana-cli` — renamed in newer images).
- `python3` started silently resolving to a different interpreter
  (Homebrew's 3.14) after installing `node_exporter` pulled it in as a
  dependency, shadowing the Python 3.9 that had `streamlit` installed.
  Fixed by calling `/usr/bin/python3` directly.
- Grafana's host port changed from 3000 → 3099 in `docker-compose.yaml` to
  resolve a local port conflict — this is now the committed default, not a
  personal workaround.

## Immediate next task: conversion history store

Agreed design, not yet started:

- **SQLite as the always-on default** (standard library, zero new
  dependency, works fully offline). A `conversions` table recording every
  conversion: timestamp, panel title/type, success/error, tier, ES|QL,
  confidence/explanation/approximations/`attempt_history` for Tier 2,
  whether/where it was imported to Kibana.
- **Elasticsearch as an optional, eventually-consistent downstream
  projection** — not a replacement for SQLite. Two sync-tracking columns
  (`synced_to_es`, `es_doc_id`) let a sync step run independently of when a
  conversion happened: find unsynced rows, push them, mark them synced. This
  means a conversion done entirely offline (no Kibana creds yet) still gets
  captured locally and can be backfilled to ES later.
- Needs the **Elasticsearch** endpoint specifically for writing documents
  (not the Kibana endpoint currently collected in `app.py` for Saved Objects
  import) — `.env` already has both (`ES_ENDPOINT` vs `KIBANA_ENDPOINT`), so
  this is just a second UI field, not a new credential type.

Proposed build order (small steps, test each before moving on, per this
project's established working style):
1. `conversion_store.py` — SQLite layer alone (init, insert, query,
   mark-synced). Test standalone first, no UI or ES involved.
2. Wire into `app.py` so every conversion gets recorded automatically.
   Verify a row actually lands in the `.db` file after a real conversion.
3. Add a **History** view to the Streamlit app, reading from SQLite. Useful
   on its own, independent of ES.
4. Add the ES sync: a second endpoint field + a "Sync to Elasticsearch"
   button, writing to an index (e.g. `prom-demo-conversions`). Validate
   documents land correctly via Dev Tools.
