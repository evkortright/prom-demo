# Session Handoff — 2026-09-25

## What this project is

`prom-demo` is a proof-of-concept tool that normalizes raw Prometheus metrics
to OpenTelemetry semantic conventions before indexing into Elasticsearch. It
solves a real problem: when Prometheus `remote_write` sends data to Elastic,
field names are flat and underscore-style (`method`, `status_code`, `job`),
which is incompatible with OTel-native traces and logs that use dot-notation
semconv names (`http.request.method`, `http.response.status_code`,
`service.name`). The mismatch silently breaks cross-signal correlation.

The approach: an OTel Collector pipeline scrapes the Prometheus `/metrics`
endpoint, applies a mapping table via OTTL transform processors, and exports
OTel-compliant data to Elasticsearch using the `elasticsearchexporter` in
`otel` mapping mode. Data lands in `metrics-*.otel-*` data streams with proper
OTel field structure, separate from raw PRW data.

The broader vision (from `docs/handoffs/` and the original design session) is
a standalone, operator-deployable tool for any Prometheus user migrating to
Elastic Observability — not just the prom-demo app, but any real Prometheus
deployment scraping Node Exporter, kube-state-metrics, application exporters,
etc.

## Architecture

```
prom-demo Go app (:8080/metrics)
    │
    │  prometheus receiver — scrape every 15s
    ▼
OTel Collector (otel/opentelemetry-collector-contrib:latest, v0.161.0)
    │  processors (in order):
    │    memory_limiter
    │    resourcedetection       → adds host.name, os.type from container
    │    transform/resource_promotion → promotes env, region, host_name
    │                                   from datapoint to resource attributes
    │    transform/universal     → job → service.name, instance → service.instance.id
    │    transform/http          → method/path/status_code → OTel HTTP semconv
    │    transform/grpc          → grpc_* → rpc.* semconv
    │    transform/database      → db_* → db.* semconv
    │    transform/metric_names  → Prometheus names → OTel metric names
    │    batch
    ▼
Elasticsearch exporter (mapping mode: otel)
    ▼
metrics-prometheusreceiver.otel-default (Elastic Serverless)
```

Prometheus also runs in the stack (for local PromQL queries at localhost:9091)
but does NOT remote_write to Elasticsearch — the Collector handles all export.

## What works (as of this session)

### Three mapping domains, fully implemented and tested:

**HTTP:**
- `method` → `http.request.method`
- `path` → `url.path`
- `status_code` → `http.response.status_code` (cast to integer)
- `http_requests_total` → `http.server.request.count`
- `http_request_duration_seconds` → `http.server.request.duration`

**gRPC:**
- `grpc_service` → `rpc.service`
- `grpc_method` → `rpc.method`
- `grpc_code` → `rpc.grpc.status_code`
- `grpc_type` → `rpc.grpc.stream_type`
- `grpc_server_handled_total` → `rpc.server.request.count`
- `grpc_server_handling_seconds` → `rpc.server.duration`

**Database:**
- `db_system` → `db.system.name` (values already OTel-compliant: postgresql, redis)
- `db_name` → `db.namespace`
- `db_operation` → `db.operation.name`
- `db_query_duration_seconds` → `db.client.operation.duration`
- `db_connections_active` → `db.client.connection.count`
- `db_errors_total` → `db.client.operation.errors`

**Resource attributes (universal):**
- `job` → `resource.service.name`
- `instance` → `resource.service.instance.id`
- `env` → `resource.deployment.environment.name` (promoted from datapoint)
- `region` → `resource.cloud.region` (promoted from datapoint)
- `host_name` → `resource.host.name.scrape` (logical name; `host.name` = container ID from resourcedetection)

**Go runtime (partial — extend in next session):**
- `go_goroutines` → `go.goroutine.count`
- `go_memstats_heap_inuse_bytes` → `go.memory.heap.used`
- `go_memstats_heap_idle_bytes` → `go.memory.heap.idle`
- Several others — ~10 mapped, ~20 remaining

**Original labels preserved:** All original Prometheus labels remain on the
document alongside OTel attributes. Backward compatibility is intentional.

## Critical technical discoveries (don't re-learn these)

### 1. PRW endpoint bypasses `@custom` ingest pipeline on Serverless
The Elastic Serverless Prometheus remote_write endpoint (`/_prometheus/api/v1/write`)
writes directly to the TSDB layer, skipping the entire Elasticsearch ingest
pipeline machinery. The `@custom` pipeline hook that works for standard data
streams does NOT fire for PRW traffic on Serverless. This is by design — it's
a high-throughput optimized path. The ES ingest pipeline in `prom-otel-pipeline/pipeline.json`
is preserved for reference and works correctly (validate with `_simulate`), but
cannot be applied to live PRW data on Serverless. The OTel Collector is the
correct solution.

### 2. OTTL context rules
In the OTel Collector transform processor, context determines what paths are valid:
- `context: resource` → use `attributes["key"]` for resource attributes
- `context: datapoint` → use `attributes["key"]` for datapoint attributes,
  `resource.attributes["key"]` for resource attributes
- `context: metric` → use `metric.name` for the metric name; cannot access
  `datapoint.attributes` from here
- `delete_key(attributes, "key")` is the correct OTTL function (not `delete()`)

### 3. counter_double in ES|QL
Metrics mapped as monotonically increasing counters land in Elasticsearch as
`counter_double`. ES|QL will reject `MAX()`, `MIN()`, `SUM()`, and `COUNT()`
on counter fields. The workaround is `TO_DOUBLE()`:

```esql
| EVAL c = TO_DOUBLE(http.server.request.count)
| STATS total = MAX(c) BY `http.request.method`
```

Use `COUNT_DISTINCT()` instead of `COUNT()` for cardinality checks on any field.
Use `RATE()` or `INCREASE()` for true time-series rate calculations.

### 4. Data stream naming
The OTel Collector's `elasticsearchexporter` in `otel` mode derives the data
stream name from the job label in the scrape config. With `job_name: "prom-demo"`,
data lands in `metrics-prometheusreceiver.otel-default` — the dataset segment
comes from the receiver name, not the job name. This is a known behavior of the
exporter. To control naming, use the `data_stream` settings in the exporter config.

### 5. OTel exporter promotes semconv attributes to top-level
The `elasticsearchexporter` in `otel` mode automatically promotes OTel semantic
convention attributes to top-level Elasticsearch fields. `http.request.method`
appears as both `attributes.http.request.method` AND as a top-level `http.request.method`
field. ES|QL queries against top-level fields work directly without dot-escape:
`http.request.method` not `` `http.request.method` `` (though both work).

### 6. Static scrape labels land as datapoint attributes, not resource
When you add labels to `static_configs` in the Prometheus scrape config (e.g.
`env: production`, `region: us-central1`), the OTel Collector's prometheus
receiver puts these on datapoints, not on the resource. The
`transform/resource_promotion` processor exists specifically to lift them to
resource level and remove the datapoint copies.

### 7. Python 3.9 compatibility
The test runner (`run_tests.py`) was written for Python 3.9 compatibility.
Use `Optional[str]` not `str | None`, `List[...]` not `list[...]`, `Dict[...]`
not `dict[...]`. The user's Mac runs Python 3.9 (system) via `/usr/bin/python3`.

## Immediate next steps (priority order)

### 1. Fix data stream naming (quick win)
The data stream name `metrics-prometheusreceiver.otel-default` is derived from
the receiver name, not the job. Add explicit data stream configuration to the
elasticsearch exporter to get a cleaner name like `metrics-prom-demo.otel-default`.
Research: `data_stream.dataset` and `data_stream.namespace` settings in
`elasticsearchexporter`.

### 2. Extend Go runtime mapping table
~10 Go runtime metrics are mapped, ~20 remain. The full list is visible in ES:
look for `go_memstats_*` fields in the catch-all document. Map them to OTel
Go instrumentation semconv names. Low complexity, high coverage value.

### 3. Node Exporter domain
The single most important domain after HTTP/gRPC/DB for real-world Prometheus
deployments. Node Exporter emits system metrics with labels like `cpu`, `mode`,
`device`, `fstype`, `mountpoint`. Map these to OTel `system.*` semantic
conventions. Add a Node Exporter container to docker-compose.yaml for testing.

### 4. kube-state-metrics domain
The second most important domain for Kubernetes deployments. Labels like
`namespace`, `pod`, `container`, `deployment` map to OTel `k8s.*` conventions.
Requires a Kubernetes environment to test properly — may defer.

### 5. Dashboard migration layer
The original project vision from `migration-tool-assessment-and-vision.md`:
take a Grafana panel JSON, extract semantic intent, generate the equivalent
Kibana panel using normalized OTel field names. This is the payoff for building
the normalization layer — once fields are OTel-compliant, dashboard migration
becomes semantic translation rather than syntax rewriting.
